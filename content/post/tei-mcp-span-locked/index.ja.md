[初めてtei-mcpについて書いた](/post/tei-mcp/)とき、目標はAIアシスタントがTEIマークアップをでっち上げるのを止めることでした。スキーマによるグラウンディングは問題の一部を解決しました。P5仕様への直接的でツールベースのアクセスがあれば、モデルはもはや要素の意味やそれが受け入れる属性を推測する必要がありません。出力は検証を通ります。

しかし、TEIエンコーディングにおけるハルシネーションには二つの顔があり、スキーマが捉えるのはそのうちの一つだけです。仕様に照らした検証は、*マークアップ*が整形式であることを教えてくれます。しかし、そのマークアップが包む*テキスト*については何も語りません。そしてそこ――テキストそのもの――にこそ、より有害なハルシネーションが潜んでいるのです。v0.3の目玉機能であるスパン固定合成は、まさにそれを防ぐために設計されています。

## スキーマが捉えられないハルシネーション

モデルに16世紀のフランス語の手紙をエンコードするよう頼むと、多くの場合、非の打ちどころがないように見えるTEI文書が返ってきます。ヘッダーは埋められ、`<persName>`タグは正しく配置され、`<dateline>`は整形式です。`validate_document`にかければ、通ります。

そこで本文を原文と比較してみてください。

`mesme`が`même`になっています。コンマが移動しています。`luy`が黙って`lui`に現代化されています。写本で読みにくかった節が、より綺麗なものに「訂正」されています。これらの変更はどれも要求されていません。どれもフラグが立てられていません。文書はスキーマ的には妥当で、ひそかに間違っているのです。

エンコードされたテキストが、下流の読者、検索インデックス、引用が依拠する恒久的な記録となるアーカイブのワークフローにとって、これは最も重要な障害モードです。不正なタグは煩わしいものです。しかし、5年間誰も気づかない現代化された綴りは、汚損です。

## スパン固定合成

新リリース（v0.3）は、まさにこの障害モードを狙ったハルシネーション防止機構を搭載しています。設計目標は、本文のハルシネーションを単に起こりにくくするのではなく、構造上不可能にすることです。

考え方は単純です。**モデルは決して本文を入力しない**のです。

代わりに、ワークフローは次のように進みます。

1. モデルは`get_source("letter_001")`を呼び出し、原文のプレーンテキストを不変の文字列として受け取ります。
2. 適用したいタグごとに、`tag_span("letter_001", start, end, element_path, attrs)`を呼び出し、原文上の文字範囲にTEI要素を登録します。
3. 完了したら、`compose("letter_001")`を呼び出します。サーバーは記録されたタグを元のプレーンテキストと組み合わせ、最終的なTEIをレンダリングし、その後、レンダリングされた文書の平坦なテキスト内容が原文と等しいことを*バイト単位で*検証します。

バイトが一致すれば、文書が返されます。一致しなければ――モデルのタグが何らかの形で、原文と1文字でも異なる本文を含意するなら――`compose()`は汚損した文書を返す代わりに例外を送出します。

このワークフローには、モデルが原文と本文の異なるTEI文書を生成する経路は存在しません。この不変条件は機械的なものであり、振る舞いに依存するものではありません。モデルがハルシネーションを起こさないと信頼する必要はなく、2つのバイト列の間の`==`チェックを信頼すればよいのです。

## これは何であり、何でないか

スパン固定合成はスキーマ・グラウンディングを**補完する**ものであり、置き換えるものではありません。スキーマ・グラウンディングのツール群（`validate_document`、`lookup_element`、`valid_children`、およびもとの16個の残り）は、モデルが*妥当な*TEIを生成するのを助けます。スパン固定合成は、そのTEIの中の本文が原文に*忠実である*ことを保証します。実際に運用できるエンコーディングのワークフローは両方の軸を満たさなければならず、今や両方が単一のサーバーでカバーされています。

これはまた、あらゆることに効く魔法の修正でもありません。`compose()`は、登録されたタグが読み込まれたODDカスタマイズのもとで許容されるかどうかをまだ確認しません。それは今後の課題です。記録されたタグはプロセスのメモリ内にあり、再起動後は残りません。また、原文ファイルはサーバーが動作する場所から読める必要があります。これらはすべて対処可能であり、いずれも中核となる不変条件を損なうものではありません。

## TEIを超えてなぜ重要か

このパターンは一般化できます。モデルにテキストの注釈付け、変換、ラッピングを求めるときはいつでも、そして基礎となるテキストの完全性が、モデルがそれを「改善」する能力よりも重要であるときはいつでも、同じ形の解決策が当てはまります。モデルにテキストを打ち直させてはいけません。テキストに対する指示を生成させ、決定論的なコンポーザーに等価性の不変条件のもとでそれを適用させるのです。

特にデジタル版にとって、これは責任をもってモデルに任せられることの範囲を変えます。エンコーディングは突如として、すべての出力を手作業で原文と比較することなく委任できるタスクになります。機械が退屈な道を引き受け、編集者は綴りではなくマークアップをレビューするのです。

## アップデートの入手

すでにtei-mcpをインストールしている場合：

```bash
uvx tei-mcp@latest
```

新規の場合：

```bash
pip install tei-mcp
```

スパン固定合成を使うには、サーバーに原文プレーンテキストファイルのディレクトリを指定します。

```bash
export TEI_MCP_SPAN_SOURCE_ROOT=/path/to/sources
uvx tei-mcp
```

各ファイルのステム（拡張子を除いた名前）が文書IDになります（`letter_001.txt` →
`letter_001`）。

ソースコード、完全なドキュメント、および不変条件の設計ノート：
[github.com/Pantagrueliste/tei-mcp](https://github.com/Pantagrueliste/tei-mcp)
